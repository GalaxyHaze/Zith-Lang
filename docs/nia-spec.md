# NIA Spec - Numeric Interval Analysis (Draft)

This document is a future-design spec for Numeric Interval Analysis (NIA),
previously described as NTA. It is intentionally *not* ownership analysis.
NIA collects and solves numeric facts; NRA, RRA, and MRA consume those facts.

## 1. Scope

NIA proves constraints such as `i >= 0`, `i < len`, `x == y + 4`, and
`value in 2..=7`. It does not decide whether a borrow is legal, whether a
memory region is writable, or whether a low-level address is valid.

The facts generated by NIA are the numeric substrate used by:

- RRA, to compare slice/array subranges;
- MRA, to verify accesses fit a declared memory region;
- HIR/codegen, to mark bounds checks that are already proven.

## 2. Versioned Fact Store

NIA uses a versioned fact store shaped like SSA. A fact is identified by a
fact id plus a version; writes create a new version, reads only produce new
known facts.

```text
FactRef := (FactId, VersionId)
```

### 2.1 Reads

A read does not invalidate prior facts. It creates a query environment that
inherits the current facts and adds newly discovered facts:

```text
if (i >= 0 && i < values.len) { ... }
```

Inside the true branch, NIA adds:

```text
i >= 0
i < values.len
```

### 2.2 Writes

A write creates a new version of the target and keeps only facts that remain
provable after the write. For a call, that means only the facts that the
function header exposes.

```text
values[i] = next;   // updates values, version v1 -> v2
```

The new version carries the caller-visible slice/array relation and the header
facts, not arbitrary internal facts from the callee.

## 3. Function Headers

Every analyzed function may expose an `NiaFunctionHeader`. The header is
recursion-free: a call site applies the header instead of reanalyzing the
callee body.

```text
fn sum(values: []i32, start: i32) -> i32

nia header:
  pre:     start >= 0
  reads:   values
  writes:  none
  post:    ret >= start
  visible: values.len
  pure:    true
```

Fields:

| Field | Meaning |
|---|---|
| `pre` | Numeric preconditions the caller must satisfy. |
| `reads` | Facts the function may read. |
| `writes` | Facts/values the function may create a new version of. |
| `post` | Numeric relationships visible after the call. |
| `visible` | Known facts exposed to callers without invalidating hidden state. |
| `pure` | If true, the header can be shared across call sites. |

If the function is pure and the header inputs are compatible, call sites may
share the same fact results. If the function is impure or depends on state not
represented in the header, each call receives a unique use id so versions do
not leak across calls.

## 4. Control Flow

NIA does not prove recursively while walking expressions. It first collects
the reachable control-flow premises, correlates shared premises into a small
premise graph, groups them, and then resolves each group. This is deliberately
a three-phase model:

1. **Collect**: walk the function once and record facts and premises per
   block/expression. Do not expand every control-flow path literally.
2. **Group**: correlate premises that share facts. If one premise becomes
   contradictory, invalidate the shared node once and discard every dependent
   group together.
3. **Resolve**: solve the remaining groups in dependency order. A group is
   not recursively re-entered.

For a branch:

```text
if (cond) { A } else { B }
```

- the `cond` path inherits the pre-branch facts plus `cond`;
- the else path inherits the pre-branch facts plus `not cond`;
- contradictions are discarded and recorded as conflicts;
- a join keeps only facts proven on every surviving path.

Query results use four states:

| State | Meaning |
|---|---|
| `True` | Every surviving path proves the fact. |
| `False` | Every surviving path disproves the fact. |
| `Maybe` | Surviving paths disagree. |
| `Unknown` | No surviving path proves or disproves the fact. |

A contradictory path is never promoted to `Maybe`. It is discarded and
reported as a conflict, matching the `FactStore` join model in `Zith-Lang`.

### 4.1 Shared Premises

Premises are correlated, not exploded into independent paths. Two branches
that share a precondition reference the same premise node:

```text
P:  values.len == 8
  /               \
A: i >= 0        B: i < values.len
  \               /
      join
```

If `P` is invalidated later, both `A` and `B` are discarded through their
dependency on `P` without re-running the whole analysis.

### 4.2 Loops As Constructs

A loop is a control-flow construct, not a separate path per iteration. NIA
does not enumerate `i = 0`, `i = 1`, `i = 2`, ... as independent paths.

Instead, a loop is analyzed as a construct with:

- a pre-loop environment;
- a loop header premise;
- a body premise;
- a back-edge that feeds the next header iteration;
- a widening/fixpoint rule for counters and ranges.

```text
for (i in 0..len) {
    arr[i] = ...
}
```

NIA represents the loop as:

```text
i in [0, len)
body premise: 0 <= i && i < len
back-edge:    i' == i + 1
join:         i = merge(i, i')
```

The solver applies the back-edge to the current domain, merges with the
header, and repeats until the domain stabilizes or an analysis budget stops
the fixpoint. A stabilized loop gives `i in [0, len)` for the body and
`0 <= i <= len` after the construct.

### 4.3 Complexity Note

Shared premises reduce real compilation work by avoiding duplicated analysis
of common preconditions and by invalidating dependent groups together. In
practice this makes the common case light, but it is an amortized/structural
optimization, not a guaranteed worst-case asymptotic reduction.

The worst case still depends on the CFG, joins, fact count, versions, and
loop fixpoints:

- branches with genuinely independent facts still require those facts to be
  represented;
- every non-trivial join can require a distinct resolved fact group;
- loops require a fixpoint/widening step that may need several passes;
- `NIA_BUDGET`/`NIA_DEPTH` are the safety valves for pathological functions.

Recommendation: keep functions small and avoid monolithic bodies, matching
the project's existing design style. NIA is then expected to stay light in
the intended workloads.

## 5. Domains

NIA works with exact values, one-sided ranges, and closed/open intervals.

```text
DomainKind := Unknown | Exact | Range | Null
```

Relations:

```text
==, !=, <, <=, >, >=
```

Affine facts:

```text
x == y + 4
x == len(values) - 1
```

Affine propagation is order-independent within a path and overflow is treated
as a conflict, never as a wrapped value.

## 6. Required Extensions Over Current Facts

The current `FactStore<int>` implementation is the right foundation, but NIA
will need:

| Capability | Open gap |
|---|---|
| Unsigned lengths | Add unsigned/u64 stores for slice lengths and indices. |
| Versioned writes | Version ids per write target. |
| Header application | Call-site facts derived only from `NiaFunctionHeader`. |
| Slice length projection | `values.len` visible as a numeric fact. |
| Pure/impure reuse | Stable ids for pure calls, unique ids for impure calls. |

## 7. Example

```zith
fn first(values: []i32) -> i32 {
    if (@lengthOf(values) == 0) { return 0; }
    return values[0];
}
```

NIA can prove `0 >= 0` and `0 < values.len` after the empty-length check, so
RRA can emit `unchecked_bounds` for the `values[0]` access.
