# Zig Standard Library: Reference Notes

Accessed 2026-10-30. Stable baseline: Zig 0.17.0, released 2026-10-01, as listed on the [official download page](https://ziglang.org/download/). The local `master` snapshot is a mutable 0.18.0-dev snapshot and is not used as the stable reference here.

Links below point to the official `0.17.0` tag, with line anchors verified against the official source archive.

## Zith Constraint: Explicit State, Not Async

Zith should generally prohibit `async` and implicit coroutine suspension, using explicit `state` transitions instead. Do not copy Zig's task/future API or Go's goroutine model as the default. Zig 0.17's `Io.async` returns a `Future` with backend-dispatched `await` and `cancel`, while `Io.concurrent` can fail when concurrency is unavailable. This makes task lifecycle visible through a handle, but execution and scheduling remain delegated to the `Io` backend. [`lib/std/Io.zig:1296-1327`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io.zig#L1296-L1327) [`lib/std/Io.zig:2526-2575`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io.zig#L2526-L2575)

The Go 1.27 specification's `go` statement starts a function call as a separate goroutine and has no result handle. The function's return values are discarded, and returning from `main` does not wait for other goroutines. That model is concise but makes result collection and lifecycle coordination a separate concern. It is not a good default for Zith APIs that should expose transitions and outcomes. [Go specification, “Go statements”](https://go.dev/ref/spec#Go_statements) [Go specification, “Program execution”](https://go.dev/ref/spec#Program_execution)

Zith's existing `state` syntax declares states, transfers with `jump`, and returns a machine result through `dock`. That is explicit control transfer, not by itself a resumable I/O protocol. Prefer APIs that expose state, transition or `step`, and result values rather than hidden suspension. The right representation and ergonomics remain open design work. [`docs/09-control-flow.md:120-137`](../09-control-flow.md#L120-L137) [`docs/plans/branch-protocol.md:22-27`](../plans/branch-protocol.md#L22-L27)

## Allocators And Ownership

`std.mem.Allocator` is a small type-erased value containing implementation state and a vtable. The vtable's raw `alloc` callback returns null on failure, while the public allocator helpers and container APIs express allocation failure as `Allocator.Error!T`, where `Error` is `error{OutOfMemory}`. This is explicit error propagation, not exception-based control flow. [`lib/std/mem/Allocator.zig:14-34`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/mem/Allocator.zig#L14-L34) [`lib/std/mem/Allocator.zig:300-331`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/mem/Allocator.zig#L300-L331)

Ownership is a container-level choice. Managed containers retain an allocator and expose `deinit()`. Unmanaged containers do not retain it, so allocation, growth, and `deinit(allocator)` receive it explicitly. In both cases, the caller must pair allocation and release with the appropriate allocator. Zig's `HashMap` documents that `deinit` releases only its backing array, not keys, values, or context. Nested resources need their own cleanup. [`lib/std/hash_map.zig:135-149`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/hash_map.zig#L135-L149) [`lib/std/hash_map.zig:170-220`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/hash_map.zig#L170-L220) [`lib/std/hash_map.zig:728-760`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/hash_map.zig#L728-L760)

## Managed And Unmanaged Containers

Names are version- and container-specific. In 0.17.0, `std.ArrayList(T)` is the allocator-free `array_list.Aligned(T, null)` form. The allocator is passed to mutating operations and to `deinit`. `array_list.Managed(T)` retains an allocator but is marked deprecated. By contrast, `std.HashMap` is the managed wrapper around `HashMapUnmanaged`. The unmanaged map's `put` and `deinit` take an allocator argument. This demonstrates two useful contracts, not a universal naming rule. [`lib/std/std.zig:45-62`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/std.zig#L45-L62) [`lib/std/array_list.zig:11-20`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L11-L20) [`lib/std/array_list.zig:632-650`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L632-L650) [`lib/std/array_list.zig:680-692`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L680-L692) [`lib/std/hash_map.zig:1020-1030`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/hash_map.zig#L1020-L1030)

For Zith, the practical decision is whether an owning value stores a reusable allocator handle or requires callers to supply it on each operation. Storing it simplifies repeated methods but makes allocator identity and lifetime part of the value's representation. Passing it explicitly avoids that field but makes correct pairing the caller's responsibility.

## ArrayList Growth

`ensureTotalCapacity` asks for super-linear growth to make repeated append amortized O(1). Its 0.17.0 `growCapacity(minimum)` uses saturating addition of `minimum / 2` plus an initial allowance based on cache-line size and element size. `ensureTotalCapacityPrecise` first tries `Allocator.remap`. If that cannot resize the allocation, it allocates a new buffer, copies only live elements, then frees the old buffer. The source explicitly avoids reallocating the full old capacity because that would copy unused capacity. Growth can invalidate element pointers. [`lib/std/array_list.zig:1347-1378`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L1347-L1378) [`lib/std/array_list.zig:1550-1557`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L1550-L1557)

Allocator `resize` only succeeds without moving the pointer. `remap` may relocate, and null means the caller should allocate, copy, and free instead. In ArrayList's fallback, allocation happens before old storage is freed or the list is updated, so allocation failure preserves the old allocation and logical contents. This is a concrete failure-atomicity pattern for Zith's pending growth contract. [`lib/std/mem/Allocator.zig:35-79`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/mem/Allocator.zig#L35-L79) [`lib/std/array_list.zig:1355-1378`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L1355-L1378)

## I/O Model

`std.Io` is a type-erased I/O and concurrency context. An `Io` value carries `userdata` and a vtable, and `operate` dispatches an operation through that pair. The module exports `Reader`, `Writer`, `File`, and `Dir` submodules. `Reader` and `Writer` are buffered interfaces with their own vtables. A file reader stores both the `Io` context and `File` and exposes a `Reader` interface. The compatibility `std.fs` module in this release is only a deprecated shim for a few old names, pointing callers toward `std.Io.Dir`. [`lib/std/Io.zig:15-45`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io.zig#L15-L45) [`lib/std/Io.zig:51-57`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io.zig#L51-L57) [`lib/std/Io.zig:550-557`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io.zig#L550-L557) [`lib/std/Io/Reader.zig:13-47`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io/Reader.zig#L13-L47) [`lib/std/Io/Writer.zig:13-46`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io/Writer.zig#L13-L46) [`lib/std/Io/File/Reader.zig:1-29`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io/File/Reader.zig#L1-L29) [`lib/std/fs.zig:1-19`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/fs.zig#L1-L19)

This is broader than a file-only facade: I/O context is explicit and backend dispatch is behind a vtable, while buffered reader/writer behavior is a separate reusable layer. That separation is a stronger Zith reference than copying Zig's complete interface surface.

## JSON Architecture

The module layers tokenization, typed parsing, dynamic values, and serialization. `Scanner` emits tokens. `json.Reader` adapts `std.Io.Reader`. `parseFromSlice` and `parseFromTokenSource` deserialize into a chosen Zig type. `Value` represents runtime JSON, and `Stringify.value` writes through `std.Io.Writer`. The public `json.zig` facade exports these APIs from internal submodules. [`lib/std/json.zig:1-10`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json.zig#L1-L10) [`lib/std/json.zig:63-103`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json.zig#L63-L103)

Parsing APIs take an allocator and return error unions. The owned `Parsed(T)` wrapper holds an arena and parsed value. `deinit()` destroys the arena, so the parsed value's allocations share one explicit lifetime. `parseFromSliceLeaky` is a separate API for callers already using an arena-like lifetime. At the lower level, scanner tokens may borrow input or contain allocated payloads depending on `AllocWhen`. Allocated token payloads remain the caller's responsibility, and scanner/reader teardown does not free them. [`lib/std/json/static.zig:57-86`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/static.zig#L57-L86) [`lib/std/json/static.zig:89-123`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/static.zig#L89-L123) [`lib/std/json/Scanner.zig:115-136`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/Scanner.zig#L115-L136) [`lib/std/json/Scanner.zig:1450-1472`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/Scanner.zig#L1450-L1472)

Dynamic `Value` is a tagged union whose arrays and objects are allocator-backed containers. Stringification can target a caller-provided writer, or `valueAlloc` can return an allocated byte slice that the caller frees. This lets callers choose streaming output or owned output without changing the serializer. [`lib/std/json/dynamic.zig:13-28`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/dynamic.zig#L13-L28) [`lib/std/json/dynamic.zig:75-99`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/dynamic.zig#L75-L99) [`lib/std/json/Stringify.zig:573-577`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/Stringify.zig#L573-L577) [`lib/std/json/Stringify.zig:618-622`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json/Stringify.zig#L618-L622)

## Facade And Lessons For Zith

`std.zig` is a deliberate public facade: it re-exports modules such as `Io`, `fmt`, `fs`, `json`, and `mem`, and lifts selected types like `HashMap` and `ArrayList` to the top level. `std.mem` exports `Allocator`. `std.fmt` owns formatting and parsing helpers. This offers a useful model for a small, curated Zith facade over separately maintained modules. [`lib/std/std.zig:19-23`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/std.zig#L19-L23) [`lib/std/std.zig:45-62`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/std.zig#L45-L62) [`lib/std/std.zig:81-95`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/std.zig#L81-L95) [`lib/std/mem.zig:20-25`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/mem.zig#L20-L25) [`lib/std/fmt.zig:1-15`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/fmt.zig#L1-L15)

- Zith's repository style prohibits exceptions. Zig's `OutOfMemory` error union is therefore useful as explicit failure-propagation prior art, but not as evidence that Zith needs exception machinery. Zith's allocator currently returns nullable raw storage, while the `Result` plan still records `Result<void, E>` and panic behavior as open and `?` integration as out of scope. [`AGENTS.md:169`](../../AGENTS.md#L169) [`stdlib/std/memory/allocators/allocator.zith:3-14`](../../stdlib/std/memory/allocators/allocator.zith#L3-L14) [`docs/plans/stdlib/dynarray-result-panic.md:34-47`](../plans/stdlib/dynarray-result-panic.md#L34-L47)
- Zith documents `view` as read-only and `lend dyn` as exclusive mutable access. Zig's `Reader` and `Writer` interfaces show the amount of mutable state and error handling that such abstractions accumulate. Keep Zith's first I/O seam narrow, and require `lend` only for operations that mutate the buffer or sink. [`docs/14-polymorphism.md:35-54`](../14-polymorphism.md#L35-L54) [`lib/std/Io/Reader.zig:13-47`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io/Reader.zig#L13-L47) [`lib/std/Io/Writer.zig:13-46`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/Io/Writer.zig#L13-L46)
- Zith's allocator plan records that a stored `dyn Allocator` field now passes a focused runtime regression for struct-literal coercion, but still calls for auditing allocator use and failure-atomic growth. Treat that test as evidence for the tested path, not blanket proof of every stored-dyn lifetime or codegen case. [`docs/plans/stdlib/allocator-ownership.md:22-31`](../plans/stdlib/allocator-ownership.md#L22-L31)
- Borrow Zig's container guarantees more readily than its surface syntax: document allocator identity, deinitialization responsibility, pointer invalidation on growth, and unchanged prior state after failed growth. Those are the unresolved validation points in Zith's own `DynArray` plan. [`lib/std/std.zig:45-50`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/std.zig#L45-L50) [`lib/std/array_list.zig:1347-1378`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/array_list.zig#L1347-L1378) [`docs/plans/stdlib/dynarray-result-panic.md:5-11`](../plans/stdlib/dynarray-result-panic.md#L5-L11) [`docs/plans/stdlib/dynarray-result-panic.md:34-35`](../plans/stdlib/dynarray-result-panic.md#L34-L35)
- Zig's JSON layering suggests a Zith progression of scanner, typed parse, dynamic `Value`, then writer-based stringify. For Zith, keep each step gated on working allocator ownership, mutable `lend`/`dyn` receiver paths where needed, and a settled error/result surface rather than porting the full API at once. [`lib/std/json.zig:1-10`](https://github.com/ziglang/zig/blob/0.17.0/lib/std/json.zig#L1-L10) [`docs/plans/stdlib/allocator-ownership.md:22-31`](../plans/stdlib/allocator-ownership.md#L22-L31) [`docs/plans/stdlib/dynarray-result-panic.md:34-47`](../plans/stdlib/dynarray-result-panic.md#L34-L47)
